# Conversations and the case layer: design note (Phase 1, lane C)

**2026-11-03 · branch `claude/case-backend-76c2b9` · built and tested on a throwaway database, nothing applied or deployed.** Serves BR-2 (conversations), BR-3 (knowledge capture) and the member and authority part of BR-1 of [`BACKEND_REQUESTS.md`](../work/BACKEND_REQUESTS.md); makes concrete `master-roadmap-20261103/03_architecture.md` sections 3, 7 and 10. Interface contract: [`API_CONTRACT_CONVERSATIONS_20261103.md`](../work/API_CONTRACT_CONVERSATIONS_20261103.md). Migration: `db/forensic_records/034_conversations_and_case_layer.sql`, steps in `ops/034_conversations/README.md`.

**Rules kept.** No model writes a number; the layer stores what the engine returned and never edits it. A finished turn is immutable. "Delete" hides, and the audit keeps the fact. Nothing leaves the machine. A new model role (follow-up resolution) sits behind its own switch, OFF until measured.

## 2. Data model (schema `forensic`, every row has `tenant_id`)

**Conversations.** `conversation_thread` (owner, title and `title_source` auto/user, pinned, archived, `visibility` private/selected/case, `shared_with[]`, `forked_from_thread_id/turn_id`, `hidden_at/by/reason`, counters and the last question, headline and outcome for the rail; `scope_collection_ids[]` is reserved for cross-case threads and constrained empty: cross-case needs `collection_id` nullable, a later migration). `conversation_turn` (thread, `idx`, `parent_turn_id`, `kind` ask/edit/rerun, `edit_of_turn_id`, `rerun_of_turn_id`, `root_turn_id`, `question_text`, `resolved_text`, `frame_json`, `resolution_json`, `state` running/completed/failed/interrupted, `outcome`, headline, shape, `query_text`, `query_hash`, `result_digest`, `figures_json`, `evidence_refs`, gzip `snapshot` + `snapshot_state`, `engine_version`, `model_id`, `prompt_id`, `data_version_hash`, timings, `diff_summary`, `client_request_id`, generated `search_text` and `search_tsv`). `turn_feedback`, `case_data_version`.
**Knowledge.** `case_note`, `finding` (basis observed/inferred, `review_state`, `pinned_json`), `hypothesis`, `task`, `tag` + `tag_assignment` (one table for eight kinds of object), `saved_view`, `annotation` (the browser's timeline pin is `timeline_day` + `2026-02-03`). **Authority:** `case_member` (owner, lead, analyst, reviewer, viewer, auditor), `authority_record`. **Audit:** `case_audit_event`.

**Row-level security in two layers.** `forensic.case_role(tenant, case, subject)` returns the caller's role: a member's role, `open` when the case has no member rows (today's one-actor workspace keeps working), `none` for a non-member of a controlled case, a lead for a global admin, and `none` when no subject is set (fail closed). Policies: tenant on every table; case content needs a role other than `none`, writes a role other than viewer or auditor; a thread is visible to its owner, to the case when `visibility='case'`, to `shared_with` when `selected`, and always to an auditor member or an admin (private threads are visible to auditors, as the roadmap says); turns, feedback and tags follow their thread through its own policy; the engine's read-only role gets no grant at all. Go sets `app.tenant_id`, `app.subject_id`, `app.actor_role` per transaction and repeats the role rules to return a sentence instead of an empty list. Verified as the application role in `behaviour.sql` (10 steps) and in 24 live specs.

## 3. A turn

`POST /conversations/{id}/turns` runs the engine **synchronously** on a context detached from the request (closing the tab does not lose a three-minute answer; limit 10 minutes, then `interrupted`): (1) insert the turn `running` with an audit row and commit, so the rail already shows it; (2) read the branch's last six turns and run the optional follow-up resolver; (3) wait for a model slot (two at a time; the model serves one request at once); (4) call the `Engine` interface; production posts the question to `hybridQueryHandler` in-process, as `/query/hybrid` would, under the caller's own principal; (5) read headline, outcome, shape, rows, query, evidence references and figures from the response by code, build the snapshot and the data version; (6) finish the turn, the thread's last-turn fields and one audit row in one transaction. A failed engine call is a recorded turn with `state: failed`. The same `client_request_id` returns the existing turn.

**Streaming.** `Accept: application/x-ndjson` gives one JSON object per line, `text/event-stream` the same as server-sent events, no `Accept` one JSON answer at the end. Events: `phase` (`accepted`, `context`, `queued` with a position, `engine`, `saving`), `heartbeat` with elapsed milliseconds every 2 s, then `turn` and `done`, or `error`. **Only true phases are sent** (fake progress is forbidden by the directive). The engine reports no inner phases today: `emitPhase(ctx, name)` in the glue file forwards one as `engine.<name>`; the engine session can call it at the boundaries it already has; until then the page sees `engine` and a running clock.

## 4. Follow-up context

Each turn stores `frame_json`: what the engine's own frame reader found in the question sent (numbers, plates, dates, months, limit, hops, cues; a count of national ID numbers, never the numbers). The previous turns' questions, resolved questions, frames and headlines go to the resolver and are carried in the `EngineRequest`; today's production adapter sends the engine only the resolved question, so a frame reader that wants the history reads it from there. The **follow-up resolver** is a model role (`FORENSIC_CONVERSATION_FOLLOWUP`, default OFF, like the conversation role): given the history and a message such as "and for last week?" a schema-constrained call proposes a standalone question; **code applies a number lock**: any number, date, plate or identifier in it that is in neither the history nor the new message makes it be dropped and the message is sent as typed (`resolution.method`: `none`, `model`, `rejected`, `failed`, `reused`). The question sent is returned as `resolved_question` for "Interpreted as ..."; editing it is an ordinary edit-and-resubmit. A re-run reuses the stored resolved question. Specs use a scripted resolver; **no model was run**, and the role needs a follow-up bank (gate: zero rewrites that add a value, share resolved correctly) before it is switched on.

## 5. Snapshots and the data version

The snapshot is the engine's whole response, gzipped, so a restored turn renders with the page's existing code. Limits: 8 MiB of JSON, 1 MiB stored; over them the stored copy is **trimmed** (result rows to 200, evidence rows to 100, a note added; `snapshot_state: trimmed`), and if still too big it is `none` and the turn says it is **re-run only**. Tokens inside an old snapshot (`reading`, `lines_token`) live in the engine's memory: `live_tokens` is true only for the call that ran the turn (a hint afterwards), and the page re-runs to get those panels back.

`data_version_hash` is a SHA-256 over a canonical document read **before** the engine runs (a change during the run can only make a later re-run say "changed", never hide a change): each evidence item's current version and content hash, per typed family (row count, latest ingestion), and the settings that change figures (status, hub threshold). The document is stored once per hash in `case_data_version`, so a diff can name the files and families that moved.

## 6. Re-run, diff, "changed since"

`POST /turns/{id}/rerun` makes a new turn (`kind: rerun`) from the stored question and returns a **diff** against the run it re-ran; `GET /turns/{id}/diff?against=` gives the same for any two finished turns of a case without the engine. Parts: **outcome and headline** (before and after); **figures** (labelled figures with the numeric difference; result rows compared as sets by whole-row hash, so a reordering is `reordered`, not a change; when the first cell is unique a removed and an added row sharing it are one changed row, cell by cell; the first 50 of each class listed with exact totals; the first 200 rows are kept and a digest of all, so equality is exact and `complete: false` says the lists are partial); **evidence set** (files added, removed, or replaced by a newer version); **data version** (same hash or not; if not, the files, families and settings that differ). Equal data hash with different figures is `same_data_different_answer`, with the query hashes compared: the model wrote another query, a finding about the engine and not about the case. Each turn carries `reruns` and each thread `changed_since` for the rail's badge.

## 7. Fork, edit, share, hide, search

**Edit and resubmit** adds a sibling with the same parent (`kind: edit`); a conversation is a tree and returns `active_turn_id`. **Fork** (`POST /turns/{id}/fork`) creates a conversation owned by the caller whose first turn has the forked turn as parent (context by pointer, nothing copied). Only the owner adds turns; a member who reads a shared conversation forks it. **Share** sets `visibility`; audited. **Delete** sets `hidden_at/by/reason`, keeps the turns, hides the conversation from everyone but its owner, an admin and the case's auditors; reversible; the audit row stays. **Search** (`GET /conversations?q=`): `search_text` is the question and answer text through `forensic.search_normalize()` (lower case, Arabic yeh, kaf and heh folded to the Urdu forms, Arabic-Indic digits to Latin, marks and tatweel removed); a `simple` tsvector and a trigram GIN index serve the word-by-word substring match, so Urdu script and Roman Urdu are found without a stemmer. Fuzzy Roman-Urdu spelling (kya/kia) is a trigram-similarity step the indexes allow; not built.

## 8. Members, authority, audit

A case with **no members is open** (everyone acts as an analyst); the first `PUT /cases/{id}/members/{subject}` must make the caller the owner (an admin may name one), after which the case is **controlled**; the last owner cannot be removed. `authority_record` stores the legal basis with a computed status (`active`, `expired`, `not_yet_valid`, `revoked`); it informs and does not yet gate. Every change writes one `case_audit_event`; `forensic.case_audit_chain_status()` and `GET /cases/{id}/audit/verify` recompute the chain and name the first broken row (a row changed behind the trigger's back is found: spec).

## 9. Not built, and what is needed from others

Cross-case threads; export to the report builder (BR-4); the resolver is built, OFF and unmeasured; fuzzy Roman-Urdu search; permissions beyond six roles. **From the engine session** (optional, nothing blocks the merge): call `emitPhase(ctx, "<name>")` at its phase boundaries; persist the reading and evidence-line tokens if stored answers should keep those panels. **From the owner:** the live migration, the deploy and switching the resolver on each need the owner's word.
